# 외부 문서 품질 평가 — 결과 해설

이 문서는 `evals/document-quality/external/SUMMARY.md`의 측정 결과를 사람이 읽기
쉬운 형태로 풀어 쓴 해설이다. 원본 수치와 판정은 SUMMARY.md가 정본이며, 이
문서는 그 숫자를 어떻게 읽어야 하는지를 설명한다.

## 한 줄 요약

평가는 끝까지 정상적으로 수행되었고, 그 결과 **연결기(connector)의 문서 표면
추출기는 아직 기준 미달**로 판정되었다. 평가가 실패한 것이 아니라 평가 대상이
불합격한 것이다. 덧붙여 평가에 쓰인 계측 장비 자체에서도 결함 세 건이
발견되었다.

## 무엇을 했나

실제 외부 저장소 세 곳을 고정된 커밋에 묶어 두고, Mode A `standard` 워크플로를
처음부터 끝까지 실행했다.

| 사례 | 저장소 | 언어 |
| --- | --- | --- |
| `external-ts-prisma-rest` | `prisma/prisma-examples` | TypeScript |
| `external-py-flask-tutorial` | `pallets/flask` | Python |
| `external-mixed-online-boutique` | `GoogleCloudPlatform/microservices-demo` | C#, Go |

각 사례마다 순서를 지켰다. 사람이 소스만 보고 정답지(gold)를 작성 → 검토·수정 →
SHA-256으로 동결 → **그 뒤에야** 추출기와 문서 생성 실행. 정답지를 먼저 얼려야
결과를 보고 정답을 고치는 일이 원천적으로 불가능해진다.

문서 작성자(Writer), 증거 감사자(Evidence Auditor), 커버리지 감시자(Coverage
Sentinel), 게이트키퍼(Gatekeeper)는 각각 별개의 에이전트 프로세스로 실행했다.
한 액터가 네 역할을 겸하면 독립성 조건이 성립하지 않는다.

## 결과: 불합격

합격 조건은 다섯 가지다. **네 개는 세 사례 모두 충족**했고, 하나가 실패했다.

| 조건 | 결과 |
| --- | --- |
| 인용 정확도 100% | 충족 — 486개 주장 전부 |
| 근거 없는 주장 0건 | 충족 |
| 설명되지 않은 누락 0건 | 충족 |
| 거부된 초안 발행 0건 | 충족 |
| **중요 표면 재현율 100%** | **실패 — 75개 중 1개 (0.0133)** |

따라서 **측정된 문서 품질 개선은 주장할 수 없다.**

## 왜 불합격인가 — 원인 두 가지를 구분해야 한다

`0.0133`이라는 숫자 안에는 성격이 다른 두 문제가 섞여 있다.

**(1) 추출기가 아예 못 찾은 것 — 진짜 역량 부족.** 추출기의 인식 규칙에는 이런
것들이 통째로 빠져 있다.

- Go의 `func` 선언을 전혀 매칭하지 못한다. C#의 `public class`만 인식하므로,
  사례 3의 Go RPC 메서드는 구조적으로 보이지 않는다.
- `postRouter.get(...)`처럼 이름 붙인 라우터에 등록한 경로를 인식하지 못한다.
  사례 1에서 라우트를 하나도 찾지 못한 이유다.
- 데이터베이스 테이블, 설정 키, 비즈니스 규칙, 외부 연동에 대한 어휘가 없다.
- `.prisma`, `.sql`, `.yml`, `Dockerfile`, `.proto` 안의 표면은 검사 대상이 아니다.

**(2) 같은 것을 다르게 이름 붙인 것 — 채점 방식 문제.** 채점기는 `분류 | 이름 |
위치 | 문서유형` 네 항목이 **완전히 일치**해야 정답으로 센다. Flask 사례가
극단적인 예다. 추출기와 사람이 **동일한 라우트 8개와 테스트 파일 5개를 완전히
같은 파일·같은 줄에서** 찾아냈는데, 사람은 `GET,POST /auth/register (register)`로
쓰고 추출기는 `/register`로 써서 채점 결과가 **0점**이 되었다.

이름을 무시하고 위치만 대조한 진단 수치를 함께 기록한 이유가 이것이다.

| 사례 | 엄격 재현율 | 위치만 대조 |
| --- | ---: | ---: |
| Prisma REST | 0.0476 | 0.0476 |
| Flask | 0.0000 | 0.2456 |
| Online Boutique | 0.0990 | 0.1200 |
| 중요 표면 (합계) | 1/75 | 9/75 |

**결론은 어느 쪽으로 재도 불합격이다.** 다만 `0.0133`이라는 수치 하나만 인용하면
추출기의 실제 상태를 과장하게 된다. 정답지는 이미 동결되어 있으므로, 결과를 본
뒤 정답지나 채점기를 손대지 않고 두 수치를 나란히 보고했다.

## 감사 계층은 제대로 작동했다

세 사례 모두 **첫 시도에 통과하지 못했다.**

| 사례 | 라운드 | 1라운드 지적 |
| --- | ---: | --- |
| Prisma REST | 2 | 200개 중 1건 |
| Flask | 2 | 132개 중 14건 |
| Online Boutique | 3 | 135개 중 10건, 2라운드에서 새 결함 1건 추가 |

지적된 결함은 거의 전부 같은 유형이었다. "A이고 B이다" 형태의 복합 주장을
쓰면서 A만 증명하는 범위를 인용하고, B의 실제 코드는 인용되지 않은 다른 줄에
있는 경우다. 일부는 범위 문제가 아니라 사실 오류였다. 예컨대 어떤 주장은 폼
데이터를 전혀 보내지 않는 테스트를 인용하면서 "제목과 본문 폼 데이터"를 입력으로
주장했다.

여기서 두 가지를 배웠다.

1. **결함률이 연결기가 아니라 작성자 프롬프트 문구를 따라갔다.** 사례 1
   프롬프트는 "각 주장 줄이 자체적으로 뒷받침되어야 한다"를 강조했고 1/200이
   나왔다. 이후 프롬프트는 기계적 규칙만 강조했고 14/132, 10/135가 나왔다. 즉
   문서 품질은 도구만의 함수가 아니며, 도구에 결부한 품질 주장은 프롬프트 설계를
   함께 고려해야 한다.
2. **한 번의 감사로 한 줄의 모든 결함이 드러나지는 않는다.** 사례 3의 2라운드는
   1라운드가 이미 지적했던 줄에서 *다른* 절의 결함을 새로 찾아냈다. 교정 후에는
   지적된 절만이 아니라 줄 전체를 다시 검증해야 한다.

## 계측 장비에서 발견된 결함 세 건

세 건 모두 **합성 예제에서는 나타나지 않고 실제 저장소를 끝까지 돌려야만**
드러나는 종류였다. 증거 수집 도중에 계측기를 고치면 그 증거가 무효가 되므로,
어느 것도 수정하지 않고 기록만 남겼다.

| 결함 | 내용 | 무엇이 약해지는가 |
| --- | --- | --- |
| 인용 저계수 | 문서에 코드 블록(` ``` `)이 있으면 게이트의 인용 스캔이 어긋나 그 뒤 인용을 놓친다. 세 사례에서 재현: 179/200, 125/140, 131/146 | 게이트의 "승인"이 보이는 것만큼 강한 근거가 아니다 |
| 이름 규약 부재 | 채점기가 이름 불일치와 미검출을 동일하게 0점 처리하는데, 공유된 이름 규약이 공표되어 있지 않다 | `0.0133`이라는 수치가 실제보다 나쁘게 나온다 |
| 규칙 충돌 | 증거 감사자를 만족시키려 인용 범위를 넓히면, 커버리지 규칙이 요구하는 원문 위치 문자열이 사라진다 | 한쪽을 고치면 다른 쪽이 조용히 깨진다 |

첫 번째 결함은 특히 오해를 부르기 쉽다. 게이트가 인용을 전부 확인한 것처럼
승인했지만 실제로는 21개를 아예 검사하지 않았다. **문서가 잘못됐다는 뜻은
아니다.** 감사자가 486개 주장을 독립적으로 검토했고 모든 인용 경로와 줄 범위를
소스에 재대조했으므로 문서 자체는 건전하다. 다만 그 근거는 게이트가 아니라
감사자였다.

## 결론에 영향이 있는 것과 없는 것

| 항목 | 상태 |
| --- | --- |
| 불합격 판정 | **확실함** — 두 기준 모두 실패 |
| 발행된 문서의 품질 | **확인됨** — 단, 게이트가 아니라 감사자가 확인 |
| `0.0133`이라는 정확한 수치 | **과장됨** — 채점 방식 결함이 섞여 있음 |
| 게이트를 품질 보증 수단으로 신뢰 | **아직 이르다** — 인용 21개를 놓침 |

## 별개로 여전히 막혀 있는 것

토큰 사용량 비교(작업 큐 항목 B)는 이번에도 수행하지 못했다. 이 실행 환경이
실행별 provider 토큰 카운터를 노출하지 않고, 에이전트 단계의 소요 시간과 최대
메모리도 계측되지 않았다. 해당 항목은 추정값으로 채우지 않고 `not_exposed` /
`not_measured`로 기록했다. 따라서 항목 4의 판정은 **Inconclusive**로 유지되며,
그에 묶인 항목 6·8·9·10·11과 SDK 설치는 재개할 수 없다.

## 다음에 할 일

우선순위 순으로 정리하면 다음과 같다. 어느 것도 이번 세션에서 착수하지 않았다.

1. **계측 장비 결함 세 건을 먼저 고친다.** 고치지 않은 채로 다시 측정하면 같은
   왜곡이 반복된다. 각 수정은 공표된 수치의 의미를 바꾸므로 별도의 집중 회귀
   테스트와 함께 의도적으로 결정해야 한다.
2. **표면 이름 규약을 `GOLD_DATASET.md`에 명문화한다.** 그래야 정답지 작성자가
   채점기와 맞물리는 행을 쓸 수 있고, 이름 불일치와 미검출이 분리된다.
3. **추출기의 어휘 공백을 메운다.** Go `func`, 이름 붙인 라우터, 테이블, 설정 키,
   비즈니스 규칙, 외부 연동이 대상이다. 다만 이는 항목 4 판정이 Inconclusive인
   동안에는 착수할 수 없는 기능 확장이므로, 순서상 토큰 카운터가 노출되는 환경을
   확보하는 일이 앞선다.
